# 2026-09-25 游戏响应性能基线与优化

本轮已经建立可以重复执行的设备本地基准，并修复了 AI 配置恢复、策略包解析和开战准备的主要重复工作。**整体结论仍是 `needs_optimization`，不能宣称所有环节已达到极致平滑。** 实体小米 14 Pro 暂不可用；Windows 和 Android 模拟器分开记录。

复现入口见 [性能基准说明](../../ptcgdap/performance-bench.md)，可机器读取的汇总见 [完整证据](../../../evidence/ptcgdap/performance_20260925.json)。未经用户授权，没有提交、推送或发布版本。

## 测量条件

- Windows 11：i9-13900K、RTX 4090、Godot 4.6.1、Compatibility 渲染器。编辑器程序与 release 导出程序分别统计，不能互相计算提升比例。
- Android：API 36.1、x86_64 模拟器、4 核 / 4 GiB、宿主 GPU 加速、release APK，实际视口 1600×3555。该结果不代表骁龙手机，也没有模拟热降频。
- 两个平台的 `all` 组分别运行 3 个独立冷进程，每个进程重复 2 次，共各 255 条样本。冷进程使用全新诊断数据；没有宣称清除了 OS 文件缓存。
- 经典对战固定为玩家 575720、对手 575718、玩家先手；下载策略固定为 `reviewed-raging-bolt-ogerpon` 的相同归档。大型规则组件另用 `marnies-gift-box-turn-program-round05-5.21.0.ptcgai`。具体 SHA 保存在证据中。
- `all` 组会先做组件测试，且经典战斗先于作者战斗。它适合稳定比较，**不能当作首次直接进入作者对战的成绩**；直接入口另用 `author_start` 组。
- 首反馈记录加载提示实际提交绘制的时间，完成时间记录目标场景准备完毕，帧停顿记录逐帧间隔。不是触屏到屏幕的硬件延迟测量。

## 已完成的发布版测量

以下 P50 来自各 3 个进程内热样本；最大值与首次样本仍完整保留在 JSON 中。

| 操作 / 指标 | Windows release | Android 模拟器 release |
|---|---:|---:|
| 五个主页面导航，all 组样本最大完成时间 | 494 ms | 479 ms |
| 经典对战，热启动 P50 | 355 ms | 606 ms |
| 下载策略对战，热启动 P50 | 1,149 ms | 1,547 ms |
| 导航 / 开战首反馈，所有样本最大值 | 17.4 ms | 83.5 ms |
| 开战过程最大帧间隔 | 383 ms | 514 ms |
| 开局静止画面最大帧间隔 | 17.3 ms | 51.7 ms |
| 应用启动至首个场景采样点，最大值 | 3,035 ms | 2,176 ms |

下载策略开战尚未稳定低于 1 秒。现在先显示跨场景加载提示，后台读取和解析策略，显示当前阶段与已用时间；超过 3 秒补充等待说明，失败提供返回入口，不显示虚构百分比。即使首反馈达标，300～500 ms 的停顿依然会被基准标红。

启动测量是引擎进程内时间，未覆盖操作系统拉起应用的完整耗时，也不能证明启动画面在 1 秒内响应。

直接入口 `author_start` 另外各跑了 3 个冷进程 × 2 次。首次点击开战到准备完成：Windows P50 **2,722 ms**、Android 模拟器 **3,328 ms**；首反馈最大分别 **16.9 ms / 32.9 ms**，开战最大帧间隔 **310 ms / 367 ms**。这组数据说明首次开战还明显慢于热运行，但长准备期间已经有即时反馈。首次场景资源加载仍占很大比例。

导航也另外跑了无组件预热的独立入口：首次进入对战设置 Windows P50 **1,286 ms**、Android 模拟器 **1,527 ms**；再次进入分别约 **94 ms / 129 ms**。该组所有导航首反馈最大为 **16.9 ms / 7.5 ms**。因此不能用 all 组的“页面均小于 0.5 秒”来概括第一次打开设置页。

`menu.return` 和 `setup.open` 是基准布置场景的直接实例化成本，用来定位首次资源/界面构建开销；其同步耗时不能冒充产品按钮的首反馈。产品页面跳转的响应使用 `navigation.*`，开战使用 `battle.*_start`。

## 优化前后对照

从本任务修改前保存的文件重建隔离快照；保留此前工作区的其他修改，不使用 `HEAD` 覆盖整个仓库。只有原本干净的句柄与 V18 配置目录两个文件取自同一 `HEAD`。两边使用相同用例、策略、卡组、引擎、渲染方式与隔离方式，各 3 进程 × 2 次。

| 环节 | 优化前 P50 | 优化后 P50 | 变化 |
|---|---:|---:|---:|
| 再次打开 AI 选择列表 | 1,883 ms | 73 ms | −96% |
| 再次进入对战设置 | 2,071 ms | 151 ms | −93% |
| 大规则包校验，进程内首次 | 1,928 ms | 915 ms | −53% |
| 大规则包校验，后续 | 1,147 ms | 557 ms | −51% |
| 规则执行器构建，后续 | 1,046 ms | 545 ms | −48% |
| 下载策略开战，后续 | 2,668 ms | 1,646 ms | −38% |

这张表是 Windows 编辑器程序对照，不与上一张 release 表混算。经典对战完成时间约增加 4%（多了绘制反馈的帧），首次经典开战的最坏帧停顿从 3,217 ms 降至 463 ms。策略广场打开时间未出现稳定改善。优化后编辑器首次作者开战仍出现过 **1,256 ms** 的单次帧停顿，已保留为未解决项；其余两次约 407～415 ms，不能只挑较快的样本。

## 主要原因与落地改动

1. **恢复 AI 配置时重复枚举全部 V18 配置。** 普通规则策略也触发了模型配置的全量构建。现在先按策略 ID 判断并定位卡组，保留动态覆盖检查。最明显的选择列表和设置页卡顿来自这一层。
2. **JSON 字符串被反复逐字符处理。** 规范化与严格解析在单次调用内复用短字符串编码、UTF-16 排序键与已验证字面量；句柄散列移除生成 JSON 后再解析的往返。仍保留类型、Unicode、重复键、节点数、长度、数字规则和完整性检查。
3. **设置页和战斗页重复加载同一个完整策略。** 启动操作现在只传精确策略引用，战斗页重新校验归档并生成卡组。没有缓存旧选择窗口或跳过动作合法性检查。
4. **重活集中在同一主线程帧。** 字节捕获、严格 JSON 解析、适用时的签名计算放到一个后台任务。回到主线程后重新核对目录成员、路径、包身份、信任和 schema；执行器绑定与首个选择窗口分帧处理。
5. **后台加载等 100 ms 后转回同步。** 首次进入较大场景时正好触发长阻塞。现在保持可见加载提示并继续等待后台资源，超时后可返回重试。

模型推理本身不是这组固定对局的主要成本：Android 模拟器 4 局中，规则决策最大约 40 ms，模型策略决策最大约 50.3 ms，原生模型推理最大 0.37 ms。这不能推出所有模型、所有局面都同样快。

Windows release 另外完成 4 局，规则 / 模型策略决策最大分别 35.5 / 43.7 ms，推理最大 0.11 ms。两个平台共 8 局均正常结束，没有策略执行错误、非法动作提交、引擎拒绝、过期 worker 结果或 worker 启动失败。模型审计仍保留每局 2 次 `model_desired_count_invalid`、2 次 `model_unknown_uid` 以及强制选择等正常旁路，不能声称“所有模型回退为零”。

## 验证与剩余门槛

97 项 Godot 回归全部通过，包括包目录原有完整套件、39 个经过预处理的独立归档校验向量、句柄防篡改、JSON 一致性、设置页、场景切换及加载提示。报告工具的 8 项 Python 检查通过，包括缺少最后一轮、非数值耗时、Android 日志错误、无画面结果和跨平台误比较。

当前仍需处理或补齐：

- 首次应用启动 2～3 秒；不能用导航首反馈成绩代替启动验收。
- 未预热的设置页首次打开仍需 1.3～1.5 秒，首次直接开作者对战需 2.7～3.4 秒，依靠即时反馈与可见阶段改善等待感受。
- 执行器构建、首次选择窗口与棋盘刷新仍有超过 50 ms 的同步片段，尤其大型策略首次构建；编辑器还记录了一次超过 1 秒的异常帧。
- 长局战斗动画、结算、录像拖动、真实网络、热降频和低内存场景没有获得本轮的完整渲染性能验收。
- 小米 14 Pro、实体 ARM64 Android、macOS、Web / iOS Safari 未实测。已经提供同一 APK 构建和采集入口，不能把模拟器标签改成手机标签。

原始日志保留了退出诊断进程时的 `ObjectDB instances leaked` 警告（优化前后均存在），部分模拟器退出日志还有 GFXSTREAM 状态警告。它们没有被当作脚本成功依据；本轮也不宣称已经完成长局内存稳定性验证。

这份报告作为后续回归基线；超过门槛保留失败项，不因已有加载提示而自动放行“画面流畅”。运行时改动应按所属文件反向应用回滚，保留其他人的工作区修改。原始报告、快照和诊断产物在忽略目录 `.godot_test_user/performance/`，导出日志和凭据不进入公共证据。
