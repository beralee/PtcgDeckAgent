# 对战视觉事件系统设计

日期：2026-07-18

## 1. 结论

本次改造将现有零散动画收口为一个只读、可排队、可降级的“对战视觉事件系统”。系统从 `GameState` 的轻量快照差分和 `GameAction` 的语义中生成视觉事件，由单一播放队列消费；规则状态、卡牌效果、AI、回放数据和胜负判定都不依赖动画，也不等待动画回写。

目标不是为少数卡牌增加专属演出，而是用现有卡图、卡背、UI 控件、颜色、遮罩、粒子、Tween 和文字，覆盖当前游戏内容中所有常见状态变化：区域移动、训练家、进化、能量、昏厥与奖赏、伤害与治疗、检索与放逐、洗手牌、特性与竞技场、回合阶段和胜负结算。

本轮不增加动画速度档，也不增加任何图片、音频或视频素材。

## 2. 现状审计

### 2.1 已有能力

- `GameAction.ActionType` 已包含抽牌、进化、附着、训练家、竞技场、特性、撤退、攻击、昏厥、奖赏、伤害、治疗、弃牌、洗牌、公开展示、回合和胜负等语义。
- `BattleDrawRevealController` 已处理抽牌、手牌弃置和调换票的局部流程。
- `BattleFieldSwapAnimator` 已处理战斗区与备战区移动。
- `BattleAttackVfxController`、`BattleReadyVfxController`、`BattleDeckShuffleAnimator`、投币和竞技场背景翻页已提供可复用的视觉语言。
- `ScenarioStateSnapshot` 能证明完整状态可序列化，但包含完整卡牌数据，不适合每次动作都用于 UI 差分。

### 2.2 根本缺口

`BattleSceneRuntime._on_action_logged()` 目前只消费少量动作。更重要的是，大量通用效果和导入卡效果会直接修改 `PlayerState`、`PokemonSlot` 与 `GameState`：移动牌库/手牌/弃牌/放逐区卡牌，移动附着能量，改变伤害与特殊状态。单靠动作载荷无法覆盖这些变化，逐卡补动画载荷又会形成永久维护负担。

因此，视觉事件的事实来源必须是“状态变化”，动作日志只提供动作名称、发起者、阶段和特效意图等语义。

## 3. 设计原则

1. 规则单向：规则状态产生视觉事件；视觉层禁止修改 `GameState`、`PlayerState`、`PokemonSlot`、`CardInstance`。
2. 功能无影响：动画失败、锚点缺失、节点被释放或平台不支持某个效果时，立即完成该视觉事件，不能取消、重复或延迟规则动作。
3. 隐藏信息优先：动画能显示多少信息由观察者权限决定，不由卡牌当前 `face_up` 单独决定。
4. 全卡通用：优先由实例 ID 和区域差分覆盖现有及未来卡牌，不在视觉层识别具体卡牌效果 ID。
5. 一个通用队列：所有新增视觉事件由同一主序列拥有区域转移层；局部数字、光圈等从属反馈可以在该序列内部并行。已有且承担规则确认或隐藏信息职责的抽牌、手牌弃置、调换票控制器作为兼容所有者保留，由事件构建器互斥抑制对应通用事件，绝不重复播放。
6. 确定顺序：相同前后状态和动作语义必须生成相同的视觉事件顺序，方便测试和复现。
7. 不复制规则：视觉系统不判断卡牌是否合法、不计算伤害、不决定奖赏数量。
8. 不增加速度设置：时长由集中常量和事件规模自适应控制，不提供用户速度档。

## 4. 目标架构

```text
GameState（动作前的已展示快照）
              + 当前 GameAction + 动作后的 GameState
                              |
                              v
                 BattleVisualSnapshot
                              |
                              v
              BattleVisualEventBuilder（纯函数）
                              |
                              v
              BattleVisualSequenceController
                   |          |          |
                   v          v          v
             区域转移层    状态反馈层    横幅/结算层
                   |
                   v
             完成/安全降级（绝不回写规则）
```

### 4.1 文件边界

- `scripts/ui/battle/visuals/BattleVisualSnapshot.gd`
  - 捕获轻量快照，只保留视觉差分所需字段。
- `scripts/ui/battle/visuals/BattleVisualEventBuilder.gd`
  - 纯函数：比较前后快照，结合 `GameAction` 生成标准事件。
- `scripts/ui/battle/visuals/BattleVisualPrivacyPolicy.gd`
  - 纯函数：决定正面、卡背、仅数量或完全隐藏。
- `scripts/ui/battle/visuals/BattleVisualSequenceController.gd`
  - 队列、合并、取消、场景生命周期和输入门控。
- `scripts/ui/battle/visuals/BattleZoneTransferAnimator.gd`
  - 卡牌飞入飞出、叠放、扇形展开、牌库/弃牌/放逐/奖赏/手牌/场上锚点。
- `scripts/ui/battle/visuals/BattleStateFeedbackAnimator.gd`
  - 伤害、治疗、状态、触发光圈、回合横幅和胜负收束。

新文件放在 `visuals/`，避免继续扩大 `BattleSceneRuntime.gd`。场景只保留初始化、动作转发、刷新后同步和生命周期清理。

### 4.2 轻量快照

快照记录：

- `turn_number`、`phase`、`current_player_index`、胜者和原因。
- 竞技场实例 ID、所有者和卡引用。
- 双方区域：牌库、手牌、奖赏布局、弃牌、放逐区。
- 战斗区和每个备战槽的稳定槽位键、宝可梦堆叠、附着能量、道具、伤害、HP、特殊状态。
- 每张牌的 `instance_id`、所有者、名称、类型、卡引用和当时是否公开。
- `shuffle_count`。

快照不得复制完整 `CardData.to_dict()`，不得持久化，卡引用只在当前 UI 生命周期内使用。

区域键采用稳定格式：

- `p0.deck`、`p0.hand`、`p0.prize.0`、`p0.discard`、`p0.lost`
- `p0.active.stack`、`p0.active.energy`、`p0.active.tool`
- `p0.bench.2.stack`、`p0.bench.2.energy`、`p0.bench.2.tool`
- `stadium`

### 4.3 标准视觉事件

每个事件是普通 `Dictionary`：

```gdscript
{
    "kind": "zone_transfer",
    "sequence_group": "action:123",
    "priority": 30,
    "player_index": 0,
    "card_instance_ids": [42],
    "cards": [card_instance],
    "source_zone": "p0.hand",
    "target_zone": "p0.active.energy",
    "visibility": "face",
    "semantic": "attach_energy",
    "count": 1,
}
```

事件种类：

- `zone_transfer`：任意卡牌跨区域移动。
- `stack_change`：进化、退化、场上宝可梦堆叠变化。
- `field_move`：战斗区/备战区换位。
- `damage_delta`、`heal_delta`、`status_delta`。
- `trigger_pulse`：特性、竞技场或被动效果触发。
- `shuffle`：洗牌；必要时先收拢区域牌再抖动牌库。
- `phase_banner`：回合与阶段。
- `match_result`：胜负和原因。
- `pause_marker`：仅用于序列节奏，不影响规则。

### 4.4 差分与排序

卡牌移动按 `instance_id` 匹配前后区域。卡牌在前后都存在但区域键变化时生成移动；新增/消失只允许在初始化、回放切换或不完整状态下生成淡入/淡出降级事件。

一个规则动作可能产生多个视觉事件，固定顺序为：

1. 发起提示：训练家/特性/竞技场/回合横幅。
2. 成本：手牌打出、弃置能量、丢弃手牌。
3. 主效果：检索、附着、场上换位、伤害或治疗。
4. 状态结果：昏厥、卡牌进入弃牌/放逐区。
5. 奖赏与补位。
6. 洗牌与结束收束。

同一批同类卡最多同时显示 5 张；更多卡用“前 5 张 + 数量徽标”表达。连续同源同目标移动合并为批次，减少长连锁等待。

### 4.5 快照同步时机

- 对战场景完成首次 `refresh_all()` 后建立基线，不播放初始化差分。
- 每次 `action_logged` 到达时，用“上一个已提交快照”和当前状态生成事件，然后立即把当前快照设为新基线。
- 没有动作日志但状态刷新检测到变化时，生成 `refresh_fallback` 事件，覆盖直接状态修改或特殊流程。
- 回放加载、从回放继续、切换观察者、本地双人交接和退出场景时，清空队列并重建基线，不播放跨上下文差分。
- 同一个前后快照签名只提交一次，防止 action signal 与 refresh fallback 重复播放。

## 5. 隐藏信息策略

| 来源/目标 | 本方观察 | 对方观察 | 表现 |
|---|---|---|---|
| 自己牌库 → 自己手牌 | 正面 | 卡背 | 飞到手牌；对手只看到数量 |
| 检索且规则要求公开 | 正面 | 正面 | 双方可看具体卡 |
| 自己手牌 → 弃牌/场上 | 正面 | 正面 | 离开手牌后翻正 |
| 对手手牌 → 对手牌库 | 卡背 | 卡背 | 不泄露牌名或顺序 |
| 奖赏区交换 | 仅规则允许时正面 | 卡背 | 调换票全程卡背 |
| 牌库 → 弃牌/放逐区 | 正面 | 正面 | 到达公开区域后翻正 |
| 牌库内部洗牌 | 卡背 | 卡背 | 只表达数量与洗牌 |

隐私策略读取动作的 `PUBLIC_REVEAL` 语义和前后公开区域；不允许因为快照持有卡引用就显示隐藏卡面。测试必须证明对手的隐藏牌名不出现在视觉事件的可展示字段、Label 文本和日志中。

## 6. 动画清单与表现规范

### 6.1 通用区域移动

- 牌库、手牌、奖赏、弃牌、放逐区、战斗区、备战区、竞技场之间使用真实 UI 锚点。
- 卡牌路径采用轻微弧线、短距离先抬升、到达前减速；目标锚点不可用时退化为中心卡片与方向性淡出。
- 卡面在移动中按隐私策略显示；到达公开区域时可在后半程翻正。

### 6.2 训练家卡

- 从手牌抬升到中央，停留显示 0.32 秒；物品使用青色描边，支援者使用金色描边。
- 主效果开始后卡牌缩小飞向弃牌区；若规则把卡移到其他区域，则跟随真实目标。
- 不覆盖现有抽牌、手牌弃置和调换票专属流程；这些流程承担规则确认或隐藏信息展示，继续由原控制器拥有。通用事件构建器对对应动作做互斥抑制，其余 Boss 指令等区域转移进入统一队列。

### 6.3 进化与神奇糖果

- 进化卡从手牌飞到目标宝可梦上方，目标旧卡轻压暗，新卡放大后落位并闪一次边缘光。
- 神奇糖果先显示训练家卡，再显示进化卡跨越中间阶段落位；只根据实际堆叠差分展示，不自行推断进化合法性。
- 退化或卡牌从堆叠移除时反向飞向真实区域。

### 6.4 能量生命周期

- 手牌附能：能量卡飞到目标槽，缩为能量徽标位置并产生属性色脉冲。
- 能量移动：从原宝可梦到新宝可梦，两个目标依次闪烁。
- 能量弃置/放逐/回牌库：从附着位置飞向真实目标。
- 多能量批次略微错开，最多 5 张可见，其余用数量徽标。

### 6.5 昏厥、弃牌与奖赏链

- 伤害结算完成后，昏厥宝可梦先出现红色扫光和短促震动。
- 宝可梦堆叠、能量和道具按实际规则目标成组飞向弃牌或放逐区。
- 随后奖赏卡从奖赏区翻/飞入获奖玩家手牌；隐藏奖赏只在允许玩家视角显示正面。
- 最后再播放替补宝可梦进入战斗区，保证因果顺序清楚。

### 6.6 伤害、治疗和特殊状态

- 伤害数字从目标上方弹出，颜色由伤害/治疗区分；场上伤害 HUD 从旧值缓动到新值。
- 同一攻击对多个目标造成伤害时并行显示数字，昏厥结果等待数字结束。
- 治疗使用向上漂移和绿色回填；不显示规则未实际改变的超额治疗。
- 中毒、灼伤、睡眠、麻痹、混乱只用现有图形和颜色脉冲提示状态增减。

### 6.7 检索、磨牌与放逐

- 牌库检索：牌库展开最多 5 张可见牌，选中卡飞向目标，剩余牌收拢并洗牌。
- 随机或隐藏检索：只显示卡背与数量。
- 磨牌：卡牌从牌库逐张或小批飞入弃牌区。
- 放逐：公开卡面飞向放逐区，并以紫色缩放/淡出收束。

### 6.8 洗手牌与重置手牌

- 手牌先收拢成卡背，飞回牌库；牌库播放洗牌；新手牌从牌库分批飞出。
- 双方同时重置时，上下两侧依次错开，避免视觉重叠。
- 对手手牌全程卡背，不暴露顺序和内容。

### 6.9 特性、被动与竞技场触发

- 主动特性：来源宝可梦卡框产生蓝白光圈，中央短标签显示特性名。
- 被动特性：只在实际引发状态差分时触发较弱光圈，避免每次刷新闪烁。
- 使用竞技场：竞技场卡轻抬并发出绿色/金色波纹；竞技场替换继续使用现有背景翻页。
- 不有效果的点击不播放成功动画，继续使用现有无效操作提示。

### 6.10 回合、阶段与胜负

- 回合开始：当前玩家一侧亮度提升，中央短横幅显示“我方/对方回合”；随后才播放回合抽牌。
- 宝可梦检查：只在发生状态结算时显示小型阶段标签。
- 回合结束不增加长等待；用 0.18 秒方向扫光衔接下一回合。
- 胜负：冻结新视觉事件，完成当前最短不可分割片段后清队列；场地压暗，胜者一侧提亮，显示胜负原因，再交给现有结算界面。

## 7. 播放队列与输入

- `BattleVisualSequenceController` 维护 FIFO 队列和 `sequence_serial`。
- 每个事件必须在正常完成、节点释放、超时或取消路径触发一次完成回调。
- 新视觉队列不阻止规则动作、AI 决策、详情查看或日志滚动；玩家连续操作时，视觉事件继续排队并按软上限合并。现有抽牌确认、投币、奖赏选择等规则/模态流程保持它们原本的输入门控。
- AI 不等待动画做决策。若 AI 连续动作快于播放，队列按同一动作分组，超过软上限时合并同类事件，绝不丢弃最终状态反馈。
- 本地双人交接遮罩优先级高于动画；进入交接前清理隐藏信息动画并重建观察者基线。
- 回放默认不重放历史动画；从快照导航时只重建静态 UI，避免跨回合飞牌。

## 8. 布局与平台适配

- 动画坐标始终通过 `Control.get_global_rect()` 转换到全屏视觉层，不缓存跨帧绝对位置。
- 每个事件开始前重新解析锚点，因此横竖屏切换、窗口缩放和 Android 安全区变化不会把卡牌飞到旧位置。
- 全屏视觉层 `mouse_filter = IGNORE`，安全区与可视区域由现有布局控制器提供。
- 卡牌尺寸按源/目标矩形插值，并限制到可视区域的 18%～34%；竖屏批量展示改为扇形纵向错开。
- Windows、macOS、Android、Web、iOS 使用同一 GDScript/CSS-free 实现；移动端不依赖鼠标悬停，Web 不依赖线程或文件写入。

## 9. 性能、降级与生命周期

- 同屏移动卡视图软上限 8，批量牌最多实例化 5 个完整 `BattleCardView`。
- 快照和差分目标为每次动作低于 2 ms（60 张牌量级），不得复制纹理或完整卡牌字典。
- 视觉队列软上限 48 个事件；超过时合并相邻同类批次和数字反馈。
- 单事件硬超时 1.5 秒，完整动作组硬超时 4 秒；超时只清 UI。
- 场景退出、回放切换、观察者切换、对局结束和 `_notification(PREDELETE)` 都必须 kill Tween、释放临时节点并断开回调。
- 锚点、纹理或卡引用缺失时使用卡背/文字代理或立即完成，不抛出影响规则流程的错误。

## 10. 非目标

- 不修改任何卡牌效果、规则校验、AI 策略、牌组或伤害计算。
- 不新增专属卡牌素材、音效、3D 模型或 Shader 资源。
- 不重做现有攻击属性特效和竞技场背景资产。
- 不提供动画速度档、跳过按钮或新的设置入口。
- 不承诺在 Windows 主机上运行 macOS/iOS 原生包；这些平台以共享代码契约、导出可行性和布局测试为证据，原生设备验证需要对应硬件。

## 11. 完成标准

只有以下条件同时满足才可宣布完成：

- 第 6 节 11 类动画都有实现入口、自动测试和至少一个真实状态变化案例。
- 动画启用前后的规则终态、动作日志、胜负和卡牌总数一致。
- 隐藏信息测试无泄露。
- 现有抽牌、洗牌、换位、攻击、调换票、Boss 指令、奖赏与回放行为无重复动画或回归。
- Windows 横屏和竖屏、Web 导出、Android 导出/安装/启动/截图/logcat 全部通过。
- macOS/iOS 共享脚本加载、平台无关布局和可用导出预设检查通过；无法在当前主机进行的原生运行项明确记录，不能伪装成实机验证。
- 完整功能测试和 `ptcg-card-audit` 通过，审计报告中无新增 registry、smoke 或 interaction gap。
